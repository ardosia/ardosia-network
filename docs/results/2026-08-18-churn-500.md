## Scenario

The run maintained 500 target protocol-8 RakNet sessions for a 60-second measured window while scheduling 25 planned replacements per second, for exactly 1,500 nominal churn events.

Traffic remained the same mixed workload used by the historical `steady-500` comparison:

- unreliable, bidirectional: 20 packets/s/client, 64-byte payloads;
- reliable ordered, bidirectional: 2 packets/s/client, 256-byte payloads;
- fragmented reliable ordered, bidirectional: 0.2 packets/s/client, 4096-byte payloads;
- RTT probes: 2 probes/s/client, 32-byte payloads.

The run used 125 connections of temporary admission headroom, for a server cap of 625, while the target logical population remained 500.

## Interpretation

Continuous session turnover at 25 replacements/s did not expose lifecycle correctness problems in this historical run. Population recovered after every planned replacement, no replacement failed or timed out, the schedule did not miss a nominal tick, and post-drain transport reconciled to the target population.

Application throughput and RTT remained essentially unchanged relative to the historical steady-500 comparison. The run pointed toward runtime/session-maintenance CPU work rather than reliability or correctness failure.

The historical `steady-1000` profile found distributed runtime/session-maintenance overhead rather than a single dominant packet-processing hotspot, including Tokio scheduling/notification work, session maintenance, timekeeping, allocator activity, channels, and synchronization. This churn evidence did not justify a speculative RakNet correctness patch.

The load generator's higher RSS under churn was benchmark-driver behavior to investigate separately from server transport performance.

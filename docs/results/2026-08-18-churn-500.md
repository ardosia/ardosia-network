## Scenario

The run maintained 500 target protocol-8 RakNet sessions for a 60-second measured window while scheduling 25 planned replacements per second, for exactly 1,500 nominal churn events.

Traffic remained the same full mixed workload used by `steady-500`:

- unreliable, bidirectional: 20 packets/s/client, 64-byte payloads;
- reliable ordered, bidirectional: 2 packets/s/client, 256-byte payloads;
- fragmented reliable ordered, bidirectional: 0.2 packets/s/client, 4096-byte payloads;
- RTT probes: 2 probes/s/client, 32-byte payloads.

The churn benchmark used 125 connections of temporary admission headroom, for a server cap of 625, while the target logical population remained 500.

## Interpretation

Continuous session turnover at 25 replacements/s did not expose lifecycle correctness problems. Population recovered after every planned replacement, no replacement failed or timed out, the schedule did not miss a nominal tick, and post-drain transport reconciled to the target population.

Application throughput and RTT remained essentially unchanged relative to the trusted steady-500 baseline. The server consumed roughly one CPU-core-equivalent during the measured churn window while whole-host CPU remained low, making CPU scalability and runtime/session-maintenance overhead a more relevant next investigation than reliability or correctness changes.

The earlier `steady-1000` CPU profile found distributed runtime/session-maintenance overhead rather than a single dominant packet-processing hotspot, including Tokio scheduling/notification work, session maintenance (`prune_idle_sessions`, `Session::on_tick`), timekeeping, allocator activity, channels, and synchronization. The churn evidence does not justify a speculative vendored RakNet correctness patch.

The load generator's higher RSS under churn should be investigated separately from server transport performance if benchmark-driver efficiency becomes important.

## Decision

The canonical `churn-500` correctness experiment is successful on commit `e0b501288486d0c837eee9f18a4f41518382637b`.

Before declaring the overall phase complete, run the final non-heavy verification gate on that same source tree:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test --manifest-path vendor/raknet-rust/Cargo.toml --lib
git status --short
```

No vendor optimization should be made solely from this churn result. The next performance phase should use fresh paired baselines and profiling to investigate CPU scalability/runtime architecture before changing RakNet internals.
